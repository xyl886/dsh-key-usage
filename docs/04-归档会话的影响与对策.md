# 04 · 归档会话的影响与对策

> 调研对象：DSH 桌面端「会话归档」机制，以及它对 dsh-key-usage「会话用量 / 项目用量」统计口径的影响。
> 调研方式：**只读**。读发布包源码 + 读本机文件与进程；未对宿主发起任何 HTTP 请求，未改动除本文件外的任何文件。
> 调研时间：2026-10-13（本机时区 UTC+8）。

标注约定：

- **【实测】**：本次在本机读到的文件、目录、进程事实，可复现。
- **【源码确认】**：读发布包 / 本仓库源码确认的执行路径。
- **【推断】**：由上述两类事实推导，未直接观测。

## 1. 结论速览

1. **【源码确认】「归档」不是文件操作，而是一次逻辑标记写入。** 归档目录 `dsh-session-archive/` 属于第三方插件 `@linxin666/dsh-session-archive`（web profile），但真正的归档动作是调用宿主公开动词 `ctx.workspaceRegistry.archiveSession(id)`，把 session id 追加进 `~/.dsh/storages/workspace.json` 的 `global.archivedSessionIds` 数组，并同时清掉该会话的 pin；**不移动、不复制、不删除任何会话文件**。（`workspace-store.ts:70-78`、`dsh-workspace/lib/index.js:524-540`）

2. **【源码确认 + 实测】归档后 `sessionPersistence.list()` 仍然返回这些会话。** `list()` 的实现只做 `listArtifacts()` 扫磁盘 + 本进程未落盘的 pending 会话，完全不读归档集合（`dsh-session-persistence-jsonl/lib/index.js:2569-2598`）。实测：本机当前 49 个已归档 id 中，**42 个的会话目录和 `session.v4.jsonl.zstd` 仍原样留在 `~/.dsh/sessions/` 下**。

3. **【实测】背景里「当前 0 条归档」的说法只对插件台账成立，真实归档集合里已经有 49 条。** `archive-ledger.json` 是 `{"version":1,"entries":{}}`（0 条），但 `workspace.json` 的 `archivedSessionIds` **有 49 条**。说明这 49 条来自**宿主原生侧边栏「归档」菜单**，不是插件写的（插件台账为空），也说明**归档已经在本机大量发生过，而用量统计并未因此减少** —— 这本身就是最强的实证。

4. **【源码确认】真正会让「历史总量凭空变小」的不是归档，而是物理删除。** 同一插件的「自动删除 / 批量物理删除」会 `rmSync` 掉会话目录、删除 rdb 行、清投影缓存（`janitor.ts:411-483`、`session-files.ts:192-199`），文件没了 `list()` 才会少返回。该功能默认关闭（`autoDeleteEnabled: false`、`autoArchiveEnabled: false`，`config.ts:92-99`）。截止本次调研本机**未发生**插件物理删除（无 `sessions.sqlite`，126 个会话目录全部健在）。

5. **【源码确认】要「标注」归档会话，宿主有官方只读接口，不需要碰文件、不需要解压 zstd。** `ctx.workspaceRegistry.archivedSessionIds` 是公开 getter（`dsh-workspace/lib/types/index.d.ts:195`、`lib/index.js:504-505`），把它与会话 id 求交集即可打标。**推荐方案 A**：只标注、不剔除 —— 保持「归档仍计入历史总量」的口径，并在界面明确说明。

三个要点：

- 会话枚举**只看 `sessionPersistence.list()`**，不看 `sessionController` feed，也不看归档集合 → 与归档解耦；
- 日/时归属用**事件内 `event.time`**，不是文件 mtime → 归档改不动任何历史日期分布；
- 上限 `MAX_SESSIONS = 200`（`sessions.ts:21`），超出部分直接丢弃 —— 这是**独立于归档**的另一个"总量变小"来源。

### 3.1 情形一：当前（归档集合 49 条，插件台账 0 条，无物理删除）

| 指标 | 是否受影响 | 依据 |
| --- | --- | --- |
| 会话用量列表（`/dsh-key-usage/sessions`） | **不受影响**，49 个已归档会话照常出现 | `list()` 不看归档集合 |
| 项目用量（`/dsh-key-usage/projects`） | **不受影响**，归档会话的 token 继续计入其 `cwd` 项目 | 同上；`workspace` 取自 `header.cwd`（`sessions.ts:76-81`） |
| 总览 / 使用明细 / 热力图（台账链路） | **不受影响** | 走 `~/.dsh/dsh-usage/usage-ledger.json`（`ledger.ts:1-5`），与会话枚举无关 |
| 覆盖率 `coverage` | **不受影响** | 126 个会话目录全部带 zstd 产物，无 `skipped` |

**当前最反直觉的事实是：本机已经归档了 49 个会话（占 126 个磁盘会话目录的 39%），而历史总量一次都没有因此减少。** 这直接证明了「归档 ≠ 统计缩水」。

### 3.2 情形二：将来发生归档（手动或自动）

单次归档发生时：

- `list()` 返回值**不变** → 会话用量、项目用量的**总量、按天分布、热力图全部不变**；
- **没有任何指标会在归档当天"凭空变小"**；
- 唯一变化在 DSH 自身界面：该会话从侧边栏（默认"隐藏已归档"）消失、pin 被清；
- 本插件侧：**零变化**，因为 `src/**` 里没有任何归档相关分支（grep 命中 0）。

### 3.3 真正的风险：物理删除（这是唯一会让历史总量不可逆缩水的动作）

触发方式：插件管理页「批量物理删除」，或 `autoDeleteEnabled=true` 的自动清理。执行顺序（`janitor.ts:411-483`）：

```text
1. 归档标记（unarchive）                        L420-426
2. 工作区行 sessionIds 移除                     L428-434
3. 存储：deleteRdbSession + removeSessionDir    L436-461
     └─ session-files.ts:192-199  rmSync(real, { recursive: true })
4. 投影缓存 scrub（session_projcache.json + 每会话文件）  L463-464, 486-518
5. 插件归档台账清理                              L466-472
```

后果：

- 会话文件消失 → `sessionPersistence.list()` 少返回 → 会话/项目用量**永久少掉这部分**；
- 历史热力图与按天明细出现**缺口**，且不可回溯（除非另有台账快照）；
- 默认关闭（`config.ts:96`），且**执行需要本插件之外的 profile 在跑** —— 本机当前没有 `dsh web` 进程，所以风险处于休眠状态；
- 保护规则（`janitor.ts:209-226`）：当前会话、运行中会话、有运行中后代的会话、正在其它归档操作中的会话都会被跳过，绝不会为了删除而强停会话。

### 3.4 另外两个独立的"变小"来源（与归档无关，但应一并说明）

1. **`MAX_SESSIONS = 200` 截断**（`sessions.ts:21,104`）：本机 126 个会话尚未触发；一旦超过 200，最旧的一批会静默退出会话/项目统计。注释里假设"本机约 120 个 / 143 MB"，随归档积压与历史增长该假设会失效。
2. **读取失败降级**（`sessions.ts:136-138`）：`open`/`read` 抛错 → `skipped += 1` → `coverage.status = 'partial'`（`sessions.ts:212-222`）。界面能看到，但总量会静默偏小。

## 4. 可选对策

前提共识：**统计口径应保持"归档仍计入"**。归档是"从导航里收起来"，不是"用量作废"。任何"把归档会话从总量里减掉"的方案都会在归档当天造成虚假的下降，属于把噪音变成信号，不推荐。

### 方案 A（推荐）：读官方归档集合，只标注、不剔除

- **做法**
  1. `src/server/sessions.ts`：在 `createSessionSource` 的 `collect()` 里额外取一次 `host.get('workspaceRegistry')?.archivedSessionIds`，做 `session-` 前缀归一后建 `Set`；给 `SessionUsageRecord` 增加 `archived: boolean` 字段（缺失时 `false`）。
  2. `src/server/sessions.ts` 的 `sessionRowsOf` / `projectRowsOf`：行内带 `archived`；项目行额外给 `archivedSessionCount` / `archivedTokens`。
  3. `src/server/routes.ts`：`/dsh-key-usage/sessions`（L299）与 `/projects`（L321）响应体加汇总字段（如 `archived: { sessions, tokens }`），不动现有字段。
  4. `src/client/**`：会话列表行加"已归档"角标；总览与项目页脚加一句"其中 N 个会话已归档，仍计入历史总量"。
  5. 同步 `docs/01-架构与数据契约.md` 的端点字段，并按仓库规则补 `test/sessions.test.mjs`（注入假的 `workspaceRegistry`）。
- **代价**：约 80–150 行改动（服务端 ~50、客户端 ~40、测试 ~30、文档若干）。需要按 `AGENTS.md` 走完整验证：`tsc -p tsconfig.server.json` 重编 `lib/`、tsdown 重建 `client/client.js`、`node --check`、跑 `test/sessions.test.mjs` 等；**服务端改动必须退出重开 DSH 才生效**。
- **风险**：低。`workspaceRegistry` 缺失 → 全部标为未归档，口径与今天完全一致（不改变任何数字）；归档集合混用拼写 → 用归一函数防护；只读 getter，无写入风险。
- **写文件？** 否（宿主存储由宿主写，本插件只读）。
- **需要宿主接口？** 是，但**已有公开接口**：`ctx.workspaceRegistry.archivedSessionIds`（`dsh-workspace/lib/types/index.d.ts:195`）。无需宿主改动。
- **额外收益**：顺手把“归档会话仍在统计里”这件事变成界面上可见的事实，未来若真发生物理删除，用户能从"归档数"与"会话数"的对比中察觉异常。

### 方案 B：本插件自建"会话清单快照"台账

- **做法**：每次 `collect()`（或每日一次）把 `sessionPersistence.list()` 的 `{id, eventCount, revision, header.updatedAt}` 写一份快照到本插件自己的目录（例如 `~/.dsh/dsh-usage/session-snapshots/`，与现有 `usage-ledger.json` 同族）。当某 id 从 `list()` 消失时，用快照区分"归档（文件还在）/ 物理删除（文件真没了）"，并可把已删除会话的历史用量保留在总量里。
- **代价**：中高。新增写盘路径 + 保留期/轮转 + 损坏容错 + 快照与服务端编译产物的一致性；`AGENTS.md` 的"仅回环 / 不碰凭据"约束不冲突，但需要新的测试面（快照写入、损坏恢复、并发）。约 200–300 行。
- **风险**：中。引入本插件的第一处"业务数据写入"（目前 `lib/` 只读）；若快照写坏或过期，会产生"幽灵用量"，反而污染口径。且本插件当前不掌握"删除"事件，只能靠 diff 猜测。
- **写文件？** 是（新增快照文件）。
- **需要宿主接口？** 否（`sessionPersistence.list()` 已够）。
- **建议**：仅在确实需要"物理删除后仍可审计历史总量"时再做；可作为方案 A 之后的第二步。

### 方案 C：仅做口径声明与文档，不加代码

- **做法**：在 `src/client/**` 的页脚口径说明与 `docs/01-架构与数据契约.md` 里写明："归档会话仍计入统计；只有物理删除才会让历史总量下降，且不可回溯。" 不改任何数据结构。
- **代价**：约 5–15 行文案（客户端需重建 `client.js`）。
- **风险**：接近零。缺点是用户若真遇到物理删除造成的总量跳变，仍只能靠文档自救。
- **写文件？** 是（源码文案 + 文档），无新增数据文件。
- **需要宿主接口？** 否。

### 方案 D（明确不推荐）：把归档会话从统计中剔除

- **做法**：`list()` 之后过滤掉归档 id，或让 `MAX_SESSIONS` 只统计未归档会话。
- **为什么不做**：会在归档发生的当天让会话用量、项目用量、热力图**同时凭空缩小**（本机若今天生效，49 条归档记录里有 42 条的会话文件仍在盘上，会立刻少掉 42/126 ≈ 33% 的会话）；这与本插件"历史用量应稳定可审计"的定位直接冲突，且归档可随时取消，会导致总量来回抖动。
- **保留意见**：如果产品上确实需要"只看活跃会话"的视图，应作为**额外的可选过滤维度**（默认关闭）实现，而**不能**改动默认口径。

### 方案 E（与 A 配套的运维建议，非代码）

- 保持 `autoDeleteEnabled = false`（默认值）。若确实要清理磁盘，先按方案 B 落一份快照，或先用插件管理页的**预览**确认候选数量与释放空间。
- 建议不要长期无人值守地开启 `autoDeleteEnabled`：它是唯一能让历史口径不可逆缩水的开关，而且它跑在 **web profile**，`desktop` profile 侧不会收到任何提示。

### 推荐结论

**先做方案 A + 方案 C（同一次改动完成）**，理由：

1. 方案 A 的成本与风险都最低，且完全落在现有约束内（只读、仅回环、无新依赖、无需宿主改动）；
2. 它把"归档是否计入"从隐性假设变成界面上的显式事实，正是本次调研最需要固化的结论；
3. 方案 B 解决的"物理删除后仍可审计"目前是**休眠风险**（本机无 rdb、无自动删除、无 web profile 进程），不值得现在付出写盘与幽灵用量的代价；等归档/删除真正投入使用再补。
