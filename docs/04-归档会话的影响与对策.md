# 04 · 归档会话的影响与对策

> 状态：**方案 A + C 已落地（2026-10-13）** —— 服务端读归档集合给行打标记，会话列表加「隐藏已归档（默认）/ 全部 / 仅已归档」三档筛选，显示时整行淡化 + 「已归档」小标；**归档会话仍全额计入用量、项目聚合与热力图**。
> 调研方式：只读发布包源码 + 只读本机文件与进程；未对宿主发 HTTP 请求，未改动任何文件。调研时间 2026-10-13。

## 1. 结论

1. **归档 = 一次逻辑标记写入，不是文件操作**：宿主 `ctx.workspaceRegistry.archiveSession(id)` 把 id 追加进 `~/.dsh/storages/workspace.json` 的 `global.archivedSessionIds` 并清掉 pin，**不移动 / 不复制 / 不删除任何会话文件**。
2. **归档后 `sessionPersistence.list()` 照旧返回这些会话**：它的实现只扫磁盘 + 本进程 pending，完全不读归档集合。本机实测 49 个归档 id 中 **42 个的会话目录与 `session.v4.jsonl.zstd` 仍在盘上**。
3. **「归档 ≠ 统计缩水」已被本机数据证明**：本机已归档 49 个会话（占 126 个磁盘会话目录的 39%），历史总量一次都没有因此减少。
4. **唯一会让历史总量不可逆缩水的是物理删除**（第三方归档插件的批量删除 / `autoDeleteEnabled`）：它 `rmSync` 会话目录、删 rdb 行、清投影缓存，文件没了 `list()` 才会少返回。该功能**默认关闭**，且跑在 web profile —— 本机没有 `dsh web` 进程，风险处于休眠状态。
5. **标注归档有官方只读接口，不用碰文件**：`ctx.workspaceRegistry.archivedSessionIds`（公开 getter）。推荐「只标注、不剔除」。

## 2. 关键事实

| 事实 | 说明 |
| --- | --- |
| 归档的落盘动作 | 只有 `archivedSessionIds` 数组与 `pinnedSessionIds` 的变化（一次持久化写）；第三方插件额外在自己的 `archive-ledger.json` 记 `{archivedAt, source}`，所以**宿主原生归档不会在插件台账里留痕** |
| 归档的可观测副作用 | 侧边栏默认隐藏该会话、pin 被清、归档会话不能再发起模型步进；**会话文件、投影缓存、事件日志不变** |
| id 拼写 | 归档集合里 `session-<uuid>` 与裸 `<uuid>` **混用**，接入时必须归一后再比对（本机 49 条恰好全是 `session-` 前缀，但不能依赖这一点） |
| 存储服务 | `sessionPersistence` 的 `list()` / `stat()` / `open()` **没有任何归档参数或字段** |
| 第三方插件的 HTTP API | `/api/dsh-session-archive/*` 能给出完整清单，但只在装了插件的 profile 存在、依赖另一个插件，不适合作为本插件的依赖 |

## 3. 对统计口径的影响

- **归档不影响任何指标**：会话枚举只看 `sessionPersistence.list()`，日/时归属用事件内 `event.time`（不是文件 mtime），所以归档改不动任何历史日期分布；
- **两个独立的「变小」来源**（与归档无关，但应一并说明）：① `MAX_SESSIONS = 200` 截断，超出部分静默退出会话/项目统计（本机 126 个尚未触发）；② 单会话读取失败降级为 `coverage.status = "partial"`，界面能看到，但总量会偏小。

## 4. 对策与取舍

- **方案 A（已落地）**：读官方归档集合，只标注、不剔除 —— 给会话行加 `archived` 标记、项目行加已归档计数，界面加角标与页脚说明。`workspaceRegistry` 缺失时全部标为未归档，口径与今天完全一致，不改任何数字；只读、无写盘、无需宿主改动。
- **方案 C（已落地）**：页脚口径说明与 `docs/01` 写明「归档会话仍计入统计；只有物理删除才会让历史总量下降，且不可回溯」。
- **方案 B（未做）**：本插件自建会话清单快照，用于区分「归档」与「物理删除」并保留已删会话的历史用量。代价中高（新增写盘路径 + 轮转 + 损坏容错 + 幽灵用量风险），当前是休眠风险，不值得现在做。
- **方案 D（明确不做）**：把归档会话从统计里剔除 —— 会在归档当天让用量、项目、热力图**同时凭空缩小**（本机若生效会立刻少掉 42/126 ≈ 33%），且归档可随时取消，总量会来回抖动。若产品需要「只看活跃会话」，应作为**默认关闭的额外过滤维度**。
- **运维建议（非代码）**：保持 `autoDeleteEnabled = false`；要清理磁盘先用插件管理页的**预览**确认候选数量与释放空间。

## 5. 待确认（不要写成硬断言）

1. 那 49 条归档的具体时间与操作者查不到（宿主只存 id，不存时间戳；插件台账为空）；其中 7 个 id 在 `~/.dsh/sessions/` 下没有对应目录，原因未证实。
2. `sessionPersistence.list()` 在运行中的真实返回值**没有直接实测**（本次未对宿主发请求），第 1 节的结论由「源码 + 磁盘实测」推出，属高置信度推断。
