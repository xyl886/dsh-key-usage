## 1. P1 ── 提供商 API 契约汇总与兼容性加固

> 对应你的第 1 条。**这是后续所有计费/余额功能的地基**：先证明我们读得对，再谈读得准。

### 1.1 目标

把「我们实际调用 / 将来可能调用」的厂商接口，整理成一份**字段级契约**，并据此建立 fixture 与契约测试，让解析逻辑可以离线回归、字段漂移能被测试抓到。

### 1.2 覆盖范围

| 厂商 | 用途 | 现状 |
| --- | --- | --- |
| DeepSeek 官方 | 余额 + 定价（含缓存命中/未命中差异、是否错峰） | 已有 scheme，无 fixture |
| OpenCode / opencode.ai | 订阅窗口（rolling / weekly / monthly） | 已有 scheme，官方文档情况待确认 |
| OpenRouter | credits + **models 里的 pricing 字段**（天然的定价 API） | 已有 credits scheme，未覆盖 models |
| Moonshot / Kimi | 余额 + 定价页 | 已有 scheme，无 fixture |
| Z.ai / GLM | 余额 + 定价页 | 已有 scheme，无 fixture |
| 其它 OpenAI 兼容中转 | 有无余额/定价接口 | 无 scheme（需要时再补） |

> 详细的字段级契约（端点 / 鉴权 / 响应类型 / 单位 / 错误码 / 定价接口 / 文档链接）与**兼容性风险清单**由并行的调研产出，落地时并入本文件「附录 A」。

### 1.3 已经能预判的兼容性风险（按等级）

| 等级 | 风险 | 应对 |
| --- | --- | --- |
| 高 | 数值字段可能是**字符串**（余额常见 `"1.50"`），我们按 id 号处理 | 统一走 `textOf()`，同时接受 number / string |
| 高 | **200 但 body 是错误体**（部分中转商） | 解析后校验必填字段，缺失即判 `bad-json` 并回落快照 |
| 高 | OpenRouter 需要 **Management Key**，普通推理 key 会 401/403 | 文档里写明；错误文案区分「凭据被拒绝」与「权限不足」 |
| 中 | `balance_infos` 可能没有 CNY 项（或返回多币种） | 已有：优先 CNY，否则取第一项；补一条「无 CNY 时显示原币种」的提示 |
| 中 | 时间字段可能是 epoch 毫秒而非 ISO | `resetsAt` 解析同时接受 ISO 与数字 |
| 中 | 窗口缺项（没订某个周期） | 已有：缺项跳过；补测试覆盖 |
| 中 | 定价单位不同（元 / 千 token vs 百万 token） | 计费模型里显式存 `unit`（见 §2.3） |
| 低 | 限流（429） | 已有：按 `http-429` 回落；可加退避（非必须） |

### 1.4 测试方案（关键：**离线可回归**）

1. **fixtures**：`test/fixtures/providers/<provider>/<case>.json`，每个 case 存「原始响应 body + 期望解析结果」，全部脱敏（假 key、假数值）。
2. **契约测试**：`test/live-quota.test.mjs` 扩展成表驱动 —— 遍历 fixtures 调用同一解析路径，断言归一化结果（窗口键、百分比、币种、余额字段）。
3. **负例覆盖**：401/403、429、500、非 JSON、超大响应、字段缺失、类型漂移（string↔number）、空 `balance_infos`。
4. **字段漂移哨兵**：每个 fixture 记录「来源（文档链接 + 抓取日期）」；文档改版时人工更新 fixture，测试会立刻暴露解析不兼容。
5. **可选（需你授权）**：一次性真机校验脚本，用你本机凭据各打一次真实接口，把真实响应脱敏后固化成 fixture。**默认不做**，因为会联网 + 读凭据。

### 1.5 产出物

| 产出 | 位置 |
| --- | --- |
| 提供商契约汇总（总表 + 字段级 + 风险清单） | 本文件「附录 A」 |
| fixtures | `test/fixtures/providers/**` |
| 契约测试 | `test/live-quota.test.mjs`（扩展） |
| 解析容错改动（仅在测试暴露问题时才改） | `src/server/live-quota.ts` |

### 1.6 验收口径

- 每个已实现 scheme 至少 3 个 fixture（正常 / 边界 / 错误），全部通过；
- 风险清单里「高」级别的每条**都有对应测试**；
- 文档契约与 `live-quota.ts` 的实际解析逐字段对得上（附录 A 就是对照表）。

## 2. P2 ── 计费规则（✅ 已实现，未提交待验收）

> 对应你的第 2 条。目标：**成本从「估算」变成「有据可依」**，并且规则可见、可改、可追溯。
>
> **落地方式与本文原计划的三处差异**（实际以这一节为准）：
> 1. **UI 不新增 Tab**：并入「余额与配额」页下半部分（用户硬性要求），另在插件页 `plugins.bundle.config` 挂同一份面板；
> 2. **重算在服务端**（原 §2.7 写的是「无需重启宿主：计费在客户端算」）：服务端每次请求现读设置里的规则参与成本估算，因此四个 Tab 天然一致，客户端不做二次计算；规则改完**立即**生效，仍然不用重启宿主；
> 3. **台账当天的官方成本优先于用户规则**（本文原表把「用户规则」排在第一位）：官方账单金额是既成事实，用它反推/替换只会更不准；用户规则只作用在**没有官方数字**的地方。优先级最终为 **官方 > 用户规则 > 台账反推均价 > 无**。
>
> 实现位置：`src/server/pricing.ts`（纯函数）、`src/server/index.ts`（Config + 读设置）、
> `src/server/routes.ts`（`/pricing` 端点与四处成本重算）、`src/client/tabs/QuotaTab.tsx` 下半部分
> + `src/client/components/PricingRulesPanel.tsx`、单测 `test/pricing.test.mjs`（+ `test/routes.test.mjs`
> 的端到端断言）。完整的存储证据链与字段契约见 [`01-架构与数据契约.md`](./01-架构与数据契约.md) §3.13。

### 2.1 为什么现在不准

现在的成本链是：台账里有官方成本 → 用它反推每个 `provider|model` 的均价 → 再乘会话 tokens。所以：

- 台账一停更（本机停在 2026-09-30），**所有新用量都没有官方成本**；
- 均价抹平了**缓存命中/未命中**的价差（DeepSeek 这两档差很多）；
- 错峰折扣、订阅制、赠送额度全都体现不出来。

### 2.2 数据来源与优先级

| 优先级 | 来源 | 获取方式 | 覆盖度 |
| --- | --- | --- | --- |
| 0 | **台账当天的官方成本** | 台账 `cost` 字段原样 | 仅台账覆盖期内（本机停在 2026-09-30） |
| 1 | **用户手填的计费规则** | 「余额与配额」页下半部分编辑；存在宿主设置服务 | 任何厂商 / 自定义价格 |
| 2 | **厂商定价 API** | 如 OpenRouter `models` 的 pricing 字段（自动）；DeepSeek / Kimi / GLM 提供「一键套用模板」 | 有 API 的厂商自动，其余半自动 |
| 3 | **台账反推均价**（现状） | 已有 `buildPriceTable` | 台账覆盖期内可用 |
| 4 | 无 | 显示 `—` + 「未配置计费规则」入口 | — |

展示时必须标出来源：**官方 / 自定 / 估算**（避免把估算当官方数字用）。

### 2.3 计费规则的数据模型（草案）

```jsonc
{
  "version": 1,
  "currency": "CNY",
  "rules": [
    {
      "provider": "deepseek-official",     // 通配 "*" 表示兜底
      "model": "deepseek-v4.1-flash",      // 通配 "*" 表示该通道全部模型
      "unit": "perMillionTokens",          // perMillionTokens | perThousandTokens | perCall
      "input": 2.0,                        // 未命中缓存的输入价
      "cacheRead": 0.2,                    // 命中缓存价
      "cacheWrite": 2.0,                   // 写入缓存价（没有就填 0）
      "output": 8.0,
      "offPeak": {                          // 可选：错峰折扣
        "windows": [{ "from": "00:30", "to": "08:30" }],
        "input": 1.0, "cacheRead": 0.1, "cacheWrite": 1.0, "output": 4.0
      },
      "note": "来源：https://api-docs.deepseek.com/quick_start/pricing（2026-10-13）"
    }
  ]
}
```

- 匹配顺序：`provider+model` 精确 → `provider+*` → `*+model` → `*+*`（同档内按声明顺序）；
- `unit` 显式存，避免「按千 vs 按百万」错 1000 倍；
- 每条规则带 `note`（来源链接），便于复核；
- **实现补充**：`offPeak.windows` 里的 `from`/`to` 是**本地时间** `HH:MM`，`from > to` 表示跨午夜，
  `24:00` 表示当天末尾，`from === to` 视为全天；`perCall` 只用 `input` 档当每次调用价。
  窗口表达不了「仅工作日」（原模型如此，未改），DeepSeek 模板的限制写在模板 `note` 里。

> **不要改**这一条：模型与上文一致，实现里没有任何额外字段。

### 2.4 存储位置（**需要你拍板**）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 宿主设置服务** | 走宿主的 `settings` / `configForms`（dsh-context 用的 `plugins.bundle.config` 卡片就是这套） | 不直接写文件；跟宿主设置一起备份；在插件配置页可见 | 需要摸清宿主 settings API；跨 profile 不共享 |
| **B. 插件自己的文件** | `$DSH_HOME/dsh-key-usage/pricing.json` | 简单、直观、跨 profile 共享 | **打破「不写文件」的现有约束**（要写进 README/AGENTS 的权限说明） |
| **C. 只读 + 导入导出** | 规则只在界面上编辑，存在浏览器 localStorage；可导入/导出 JSON | 零写盘、零宿主依赖 | 换浏览器/清缓存就没了，不能多端共享 |

> 我倾向 **A**（最贴宿主规范）＋「导入/导出 JSON」作为兜底；B 只有在你要「跨 profile 共享」时才值得。

**已确认 A 可行 —— 并在实施时把细节核到底（读自宿主 `app.asar` + 离线实测，2026-10-13；宿主版本 0.2.0-rc.2）**：

| 事实 | 证据 |
| --- | --- |
| 宿主有按**命名空间**的配置存储，写入带乐观锁 | `settingsNamespaceRequestSchema = z.object({ ns: z.string().min(1) })` 与 `write(ns, mode, input, expectedRevision)`（`dsh-api-settings-controller/lib/index.js:260,460`） |
| 客户端有「插件/包配置」卡片槽 | 槽名 `plugins.bundle.config`（**按包名 keyed**，显示在该包详情页描述与行之间），配套 `plugins.row.config`、`plugins.item`；页面 `main` 注册时把三者声明为自己的 children（`dsh-client-ui-plugin-manager/lib/client.js:32,2522`） |
| 配置表单由宿主渲染 | `configForms` 与 `configLedgerSource`（把三类配置投影成统一的「配置账本」） |
| 远程服务 | `settingsController`（`@deepseek-ai/dsh-api-settings-controller`，`dsh-web-app` 组合里挂成 `settings-controller`）。**修正**：`describe()` **不接受参数**，返回 `{writable, hasDocument, namespaces[]}`；写方法是 `update(ns, patch, rev)` / `replace(ns, section, rev)` / `mutate(ns, ops, rev)`，`ops` 是**路径操作** `{op:'set'|'unset', path:[…], value}`，不是 JSON Patch 对象 |
| **命名空间不是自取的名字** | 就是本条目在 profile 里的 id —— 宿主 `dsh-settings` 用 `entry.options.id` 当 `ns`（`lib/index.js:432,443,502`），也就是 `cordis.patch.yml` 里 `insert.id` 的 `dsh-key-usage` |
| **可服务的前提** | 条目必须导出 schemastery 的 `Config` 且至少一个字段带 `.volatile()`；旧版 `settings.register()` 注册表已在 0.1.7 移除（第三方插件 `@liustack/modsearch/dsh/index.js:102-106` 的实测注释） |
| 插件侧读法 | 服务端 `ctx.get('settings').describe({redactSecrets:false})`（同 `dsh-context/lib/index.js:2434`）；客户端 `ctx.configForms.get(条目 id)` + `whileServed([ns], …)`（同 `dsh-context/lib/client.js:13519-13550`） |
| 宿主包怎么解析到 | launcher 把 runtime resolution 装进 Node 的 ESM / CJS 解析器；链接到树外的插件**只要把包名写进自己的 `peerDependencies`**，就按运行时表解析，不需要物理 `node_modules`（`dsh-app-boot/README.zh.md:133,134`）⇒ `@deepseek-ai/schemastery` 必须声明为 peer，否则服务端入口直接加载失败 |
| 即改即生效 | volatile 更新经 `loader._commitVolatile()` 原地改引用并发 `loader/volatile-update`，**不重挂载**（`cordis-plugin-loader/lib/index.js:375-425`） |

→ 落地方式：规则声明成插件自己的 `Config.pricing`（`.volatile()`），界面经 `ctx.configForms` 读写，
**服务端每次请求现读**（重大改动无需重启宿主）；落盘由宿主的 config-editor 原子写 profile patch 完成。
**这条路径不需要本插件写任何文件**，与「只写 `quota-snapshots.json`」的约束一致。
完整的证据表在 [`01-架构与数据契约.md`](./01-架构与数据契约.md) §3.13，离线自检脚本 `test/probe/dsh_settings_schema_probe.mjs`。

### 2.5 UI 设计（Tab 内）——实际落点

用户已拍板：**并入「余额与配额」页下半部分，不新增 Tab**。面板由 `PricingRulesPanel` 渲染，
插件页 `plugins.bundle.config` 卡片（`PricingCard`）复用同一份组件与状态。

1. **规则列表**：通道 · 模型 · 单位 · 四档单价 · 币种 · 错峰窗口（命中时挂「错峰中」）· 备注 · 编辑 / 删除；
2. **编辑表单**：通道 / 模型带通道与模型名的候选列表，单位与币种是下拉；错峰窗口与错峰价单独一组；
3. **厂商定价模板**：内置 DeepSeek / Kimi / GLM 三套（`GET /dsh-key-usage/pricing` 下发），一键套用（同键覆盖、新键追加）；
4. **成本总览**：近 30 天「规则 / 估算 / 无依据」的模型数、规则口径金额（仅参照）、
   **缓存命中省了多少钱**（按币种 + 逐模型明细）——原第 4 条「命中率-成本联动」就落在这里；
5. **导入 / 导出 JSON**、**清空规则**（即「恢复台账均价」）。

### 2.6 口径与展示规则

- 所有成本单元格统一带来源角标（`官方` / `自定` / `估算`；无依据时只显示 `—`，不挂角标）；
- 估算值在角标 tooltip 里说明依据（官方账单 / 你的规则 / 台账均价 / 无依据）；
- 多币种不换算、不合计：规则各按自己的 `currency` 算，面板上的金额按币种分行显示；
- **错峰**：规则表里标「错峰中」（按本地时间判定）；单日范围的成本按 24 小时槽的错峰占比加权。

### 2.7 验收口径（实际达成情况）

| 原口径 | 现状 |
| --- | --- |
| 手填规则后三处成本立即重算 | ✅ 四处（总览 / 使用明细 / 项目 / 会话 / 按模型）同一口径，改完立即生效、无需重启宿主（规则存在宿主设置服务，服务端每次请求现读） |
| 规则命中优先级可验证（精确 > 通配）；错峰时段切换正确 | ✅ `test/pricing.test.mjs` 覆盖四级优先级、同档顺序、本地时间 / 跨午夜 / 全天窗口、单位换算、缓存省钱 |
| 规则可导出、可导入、可一键恢复估算 | ✅ 导出 / 导入 JSON（复用 `export.ts`），「清空规则」即回到台账反推均价 |
| 台账停更场景下成本不再显示 `—`（有规则时） | ✅ 会话补位天按规则算并标「自定」 |
| 错峰价命中时显示「错峰价」+ 标准价对照 | ⚠️ **部分**：错峰窗口在规则表里标「错峰中」，单日范围按 24 小时槽算错峰占比加权；跨天范围没有小时分布，按标准价（见 §2.8） |

### 2.8 风险（实现后复核）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 用户填错单价 | 金额直接算错 | 编辑表单挡住「四档全 0」，展示公式 + 「清空规则」回到台账均价；不静默 |

### A.2 需要修 / 需要标注的风险（按等级）

| 等级 | 问题 | 处理 |
| --- | --- | --- |
| HIGH | **OpenRouter `/credits` 官方要求 Management Key**，DSH 的 openrouter 通道用普通推理 key → 会拿到 403 `Only management keys can perform this operation` | 403 单独出文案「需要管理密钥」；或改用普通 key 可用的 `GET /api/v1/key`（带 `limit/limit_remaining/usage_*`） |
| HIGH | **zai 余额端点零官方依据**；且 DSH 的 zai baseURL 是 coding 端点，coding key 受场景限制（错误码 1315） | 保留但标「未文档化、可能失效」；失败时给控制台链接而不是干等；将来改用 429 业务码里的 `{next_flush_time}` 做窗口估计 |
| HIGH | **opencode-go `/zen/go/v1/usage` 官方文档中不存在**（文档已改 `/inference/`，但 DSH 包内 baseURL 仍是 `/zen/`） | 标注「未文档化、社区逆向」；404/HTML 静默降级；结构断言不写死；请求补 `x-opencode-session` 头（官方要求客户端带稳定会话头） |
| MED | DeepSeek **不保证有 CNY 项**（国际账号可能只有 USD）；`balance_infos` 可能为空 | 已有「优先 CNY → 取第一项」；**要补**：把实际币种透传到界面，禁止把 USD 当 CNY 渲染；空数组 → 「无余额信息」 |
| MED | Moonshot 成功判定不能只看 `code`（官方示例出现过 `code:123` 占位），要看 `status===true && data` | 补判定；金额按 number 处理（允许 5 位小数与负 cash） |
| MED | Moonshot 国内外站账号/Key **完全隔离**，混用 401；余额单位是人民币元 | 401 文案提示「Key 与站点不匹配」；币种按 baseURL 判定 |
| MED | OpenRouter credits = 累计购买 − 累计使用，**不等于可用额度**；官方还写明 **200 也可能带 error 体** | UI 不要把它当「还能烧多少」；解析先查 `error` 字段 |
| MED | 「窗口」语义三家不同（OpenCode 5h=月额度 20%、Z.ai 只在错误消息里给重置时间、OpenRouter 用 ISO8601） | 保持 per-scheme 适配器，时间解析分别实现，解析失败显示原文 |
| LOW | 轮询风暴：DeepSeek 不承诺 `Retry-After`；Kimi 风控限速「一旦触发即无法解除」 | 余额轮询保持 60 s 缓存 + 失败不立即重试（可加退避） |

**一条误报（已核实，不要按它改代码）**：调研初稿推测「OpenRouter 会拼成 `/api/v1/api/v1/credits`、zai 会拼成 `/api/coding/paas/v4/api/paas/v4/balance`」——不成立。我们的 `balanceScheme` 用 `new URL(path, baseURL)`，以 `/` 开头的 path **只保留 origin**。**但要为此加测试**：断言各 scheme 在真实 baseURL 下的最终绝对 URL，防止将来有人改坏拼接方式。
