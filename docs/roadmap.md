# 后续产品向需求计划

> 来源：2026-11-24 全面审查后与作者的讨论结论。**本文件只列方向与判断依据，不代表已排期**；
> 真正的排期以作者明确指令为准，工程类事项（`routes.ts` 拆分、测试补齐）另见 `docs/process/`。

## 判断标准

按作者反复强调的三条取舍：**数据必须准确、版面不留废话、窄屏可用**。
一项需求如果只是「多显示一点东西」而说不出「解决谁的什么问题」，一律不做。

## 第一梯队（先做，收益明确）

| 需求 | 解决的问题 | 做法要点 | 预估 |
|---|---|---|---|
| **成本归因到工具 / 步骤** | 只知道一轮花了多少钱，不知道钱被什么吃掉（工具回填的大段输出是主因） | 会话事件里 `tool/call` 与 assistant 步骤都有 seq，可按「步骤增量 tokens」归因到工具名；输出「哪个工具最烧 token / 最贵」 | 2–3 天 |
| **上下文膨胀体检** | 长会话每轮都要重发全部历史，输入 token 随轮次线性上涨，页面上完全看不到 | 用每轮 `inputTokens` 画随轮次增长曲线，超阈值（如 120k）给一次提示，指明「压缩 / 新开会话」 | 1–2 天 |
| **最贵轮次 / 会话排行** | 总量看得到，定位不到具体是哪个会话、哪一轮 | 复用 `/turns` 已有数据，按会话聚合后排序，点进去落到那一轮的构成 | 1 天 |

## 第二梯队（有价值，但要等第一梯队落地）

| 需求 | 解决的问题 | 做法要点 | 预估 |
|---|---|---|---|
| **对账视图** | 官方账单与页面估算可能有差，现在无法自查 | 按天 / 模型并排展示官方金额与估算金额，列差异最大的项；差异原因写进系统日志 | 2 天 |
| **同任务多模型对比** | 同一会话内换过模型，说不清换得值不值 | 按会话内模型分段，比较 tokens / 金额 / 缓存命中 | 1–2 天 |
| **按轮明细导出** | 导出的 CSV 只有按天维度，无法复核单轮 | 增加「会话 / 轮次 / 模型 / tokens / 金额」导出 | 0.5 天 |

## 暂不做（已评估，收益不抵成本）

| 需求 | 不做的理由 |
|---|---|
| 节假日错峰 | 需要每年维护法定节假日与调休表，且只影响少数天的价格 |
| 多机数据合并 | 口径未定（合并 `usage.db` 还是 CSV、去重键是什么），贸然实现会产生对不上账的数字 |
| PNG / 图片报告 | 字体与主题在宿主里不可控，产出不稳定；导出 CSV 已能覆盖核对需求 |
| 预算告警 | 与「页面不留废话」冲突，且本地预算无法反映订阅制通道的真实支出 |
