# 开发与验收流程

> 一句话：**desktop 只装真实包、不装 `link:`；验收装 `dev` 分支的某次提交；`main` 只放已发布基线。**
> 这条规则由用户在 2026-11-20 定下，替换早期「把 desktop 切成 `link:` 到仓库」的做法。

## 分支模型

| 分支 | 作用 | 规则 |
|---|---|---|
| `main` | npm 已发布版本的基线（当前 `0.2.8`） | 只接受 `dev` 合并（`--no-ff`）；发版从 `main` 走 `.github/workflows/publish.yml`；不直接在上面开发 |
| `dev` | 集成分支、验收基线 | 提交前 `npm run verify` 必须绿；`lib/`、`client/` 产物随提交入库；**永不 force push** |
| `feat/*` | 可选短线（一批改动的隔离） | 从 `dev` 开、合回 `dev` 后删除 |

版本号分工：`dev` 用预发布号（当前 `0.2.9-dev.1`，插件页能一眼看出是验收版），`main` 的版本号仍只由发布指令推动（见 [`AGENTS.md`](../AGENTS.md) 的发布规则）。

## 为什么 desktop 不装 `link:`

- `link:` 装的是仓库目录的**当前状态**：未提交改动、没重建的旧产物都会直接进日常使用的 app；
- pnpm 不解析 link 包的 `peerDependencies`（安装时会警告），宿主还会按 link 模式处理（更新提示、热更新行为与正式包不同）；
- 出问题无法说清「当时装的是哪个版本」，回滚只能手敲命令。

## 验收安装形态（两态）

| 模式 | profile 里的依赖 | 说明 |
|---|---|---|
| registry（日常态） | `dsh-key-usage@^0.2.8` | npm 上正式发布的那一份 |
| dev（验收态） | `git+file:///D:/EasyJob/.plugin/dsh-key-usage#<提交 sha>` | pnpm 从本地 git 仓库克隆该提交并**真实安装**（hoisted 布局下是普通目录，不是 Junction），可追溯到具体提交 |

- git 来源只打包**已提交内容**，所以验收前必须把 `lib/`、`client/client.js` 一起提交，否则装到的是旧产物；
- 跨机器复现 / 里程碑验收：把同一个提交推到 GitHub 后改用 `git+https://github.com/xyl886/dsh-key-usage.git#<sha>`；
- 两种模式互切都要先 `pnpm remove dsh-key-usage` 再 `add` 目标，不要保留 Junction。

## 每次验收的动作

1. 在仓库改代码（`dev` 或 `feat/*` 上，工作区脏也无妨）；
2. `npm run verify` 全绿（会重建 `lib/` 与 `client/client.js`）；
3. 提交到 `dev`（产物一起提交）；
4. 切验收态：`D:\EasyJob\test\dsh_profile_recovery\switch-key-usage-mode.ps1 -Mode dev`
   —— 自动取 `dev` 当前提交、remove 旧包、装 `git+file://…#<sha>`、校验不是 Junction、写验收记录；
5. **完全退出 DSH 再重开**；
6. 验收通过后：`dev` 合回 `main`（`--no-ff`），等用户下发布指令再发版；
7. 回日常态：`switch-key-usage-mode.ps1 -Mode registry`。

**不要手敲 `pnpm add link:…`**；脚本还提供 `-Mode status`，随时查看当前装的是 registry 还是 dev、哪个提交、是否为 Junction。

## 兜底与排错

- 报 `ERR_PNPM_EPERM`（多见于从旧 Junction 卸载）：先完全退出 DSH，把 `node_modules/dsh-key-usage` 改名让开再装；
- 清理旧的 `node_modules/dsh-key-usage` Junction 时用 `Rename-Item`（改名让开即可），**不要**用 `Move-Item` 移进已存在的目录 —— PowerShell 会顺着链接移动目标目录的内容（实测会把仓库工作区整个搬走）；
- 装完确认 `~/.dsh/profiles/desktop/package.json` 里 `dependencies.dsh-key-usage` 与 `dsh.profile.bundles` 里的 `dsh-key-usage` **两处都在**（pnpm 不维护 `bundles`）；
- 装完若提示「请重启 DSH 使更改生效」（`package-moved`）：换安装来源后 HMR 无法热应用，重启即可，不是安装失败。

## 验收记录

脚本每次切换都会往 `D:\EasyJob\test\dsh_profile_recovery\验收记录.md` 追加一行（模式 / 版本 / 提交 / 时间）。验收出问题时先看这一行，确认当时装的是哪个提交。
